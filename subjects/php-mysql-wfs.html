Exam Writing Guide — read once, use in every answer

The only writing-strategy section: marks-wise structure, presentation rules and examiner tips

Golden rule: match your answer's length and structure to the marks. A 2-mark definition and a 7-mark explanation are different jobs — this guide gives the exact pattern for each, so individual answers below contain only academic content.

1–2 mark answers (2–5 lines)

  • Open with the exact definition or fact in one line, then add one short example or supporting point.
  • MCQs: read all four options before ticking; eliminate obviously wrong ones first and never leave a question blank.
  • Underline the keyword or formula; no introduction, no conclusion, no filler.

3–5 mark answers (½–1 page)

  • Structure: definition (2–3 lines) → 4–6 points with a mini-heading → one example or syntax line.
  • Comparisons (VS questions): always use a two-column table — Basis | A | B — with 4–6 rows, then a one-line verdict.
  • Close with a single exam-tip line, e.g. where the concept is used in real code.

6–8 mark answers (1–1½ pages)

  • Structure: introduction + definition → headings with numbered points → syntax/code/output → advantages or applications → 2-line conclusion.
  • Every program answer must show code + output + 2–3 lines explaining the logic — code alone earns partial marks only.
  • Draw the diagram or table the examiner expects (flow, ER, request–response); label it.

9–10 mark answers (1½–2 pages)

  • Treat as a mini-essay: introduction, 3–4 headed sections, comparative table or diagram, detailed example, conclusion.
  • Cover breadth (all sub-topics named) plus depth (one worked example traced step by step).
  • Budget ~15–18 minutes; if time is short, write headed bullet points rather than one long paragraph.

12–14 mark answers (2+ pages)

  • Plan before writing: jot 5–6 headings first, then expand each into a paragraph with an example or figure.
  • Compulsory elements: introduction, architecture/flow diagram, detailed explanation under headings, full program with output, comparison table, applications, conclusion.
  • Attempt these last only if confident; an organised 2-page answer beats a rushed 4-page dump.

When to use headings

  • Use headings for every answer of 4+ marks; 1–2 mark answers need none.
  • Keep headings short (2–4 words), underline them, and number points beneath (1, 2, 3…).

When to draw diagrams

  • Draw when the topic has flow, structure or interaction: request–response cycle, session handling, AJAX flow, ER/tables, architecture.
  • Simple labelled boxes + arrows beat art — always add a one-line caption and refer to it in the text.

How to present code

  • Write code in a separate indented block, one statement per line, with correct opening/closing tags.
  • Always show expected output beneath the code and underline or circle the key function or statement.
  • Mention the file name and how to run it where relevant (e.g. localhost/form.php).

How to use keywords

  • Every answer in this bank lists Keywords to Remember — memorise and underline those exact terms; examiners scan for them.
  • Prefer technical terms over vague words (say superglobal, not special variable).

Avoiding unnecessary filler

  • Never repeat the question as an introduction, and never pad with unrelated history or generic lines.
  • One idea per point; cut any sentence that would still leave the answer complete if deleted.
  • Finishing early? Re-read for spelling of function names, $ signs and semicolons — the costliest small errors.
