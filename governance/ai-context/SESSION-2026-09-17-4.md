**AWD "More options" bug — investigation and fix:**
Reproducing this required a narrow viewport. `resize_window` reported
success but `window.innerWidth` never actually changed (confirmed via
direct JS query) — this tool does not reliably control the real viewport
in this environment. Worked around it by embedding the page in a
manually-sized `<iframe>` briefly (abandoned — too unreliable, tab
navigated unexpectedly), then the browser window itself became genuinely
narrow (~220 CSS px) after repeated resize attempts, which was used for
the rest of the investigation. Pixel-coordinate clicking (`computer` tool)
was also unreliable here (screenshot dimensions shifted between calls,
20-30% off from each other) — switched to dispatching real click events
and reading DOM/computed-style state via `javascript_tool` instead, which
gave consistent, trustworthy results.

Found two distinct, compounding bugs, both pre-existing in the original
AWD file (confirmed via diff against the untouched
`Theroy Question Bank\Advanced_Web_Designing_Master_Question_Bank.html`):
1. `.dropdown{position:absolute}` nested inside
   `.control-bar{overflow-x:auto}` — clipped by the CSS spec's rule that
   `overflow-x:auto` also computes `overflow-y` to `auto`. Fixed: switched
   to `position:fixed` with JS-computed `top`/`left` from
   `moreBtn.getBoundingClientRect()`, recomputed on open and on resize.
2. After fixing #1, `document.elementFromPoint` showed a `<p>` inside
   `.site-header` still painting over the dropdown. Root cause:
   `.site-header{position:sticky;z-index:100}` outranks
   `.control-bar{position:sticky;z-index:90}`, and since the dropdown was
   a DOM descendant of `.control-bar`, its own `z-index:250` only competed
   within control-bar's local stacking context — capped below the header
   regardless of its own z-index value. Fixed: reparented `#moreDropdown`
   to `document.body` on init (a standard dropdown/modal "portal"
   pattern), so it now compares directly against page-level siblings.

**Checked PHP and NT for the same bug class** (both have a similarly-ranked
sticky-header-vs-control-bar z-index pattern) via the same
`document.elementFromPoint` technique — **neither is actually affected**;
their dropdowns already render correctly. No changes made to those files.
