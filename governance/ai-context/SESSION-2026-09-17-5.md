**Objective:** user asked to "check any issue anywhere" and make the
subject pages "look consistent" — clarified via a bundled question: they
want BOTH bug-parity across subjects AND a real shared visual design
(reversing the original "subjects keep their own themes" decision).

**Audit (before the redesign work):**
- Console errors: none on dashboard or any of the 3 subject pages (fresh
  load, checked individually).
- Searched all 3 subject files for the same bug class as the earlier
  AWT More-menu fix (popup-style `position:absolute`/`.open`-toggled
  elements nested inside a scroll/sticky ancestor with a lower z-index than
  a sibling). Found PHP's `.more-menu`, NT's `.more-menu`, PHP's
  `.focus-overlay`, AWD's `.backdrop` as the only other candidates — traced
  each one's actual DOM ancestry and, for the two "more" menus,
  empirically confirmed via `document.elementFromPoint` after opening them
  that neither is actually obstructed (unlike AWD's, which was). The two
  overlay elements are body-level siblings, not nested in the risky
  container — safe by construction.
- Functionally exercised search, bookmark toggle, and theme toggle (or the
  closest equivalent per file) on all 3 subjects via dispatched DOM events
  — all worked, no console errors.
- Inspected live `localStorage` after visiting all 3 subjects + the
  dashboard: 8 keys, all distinct
  (`nt503.theme`, `nt503.saved`, `phpwfs_theme_v1`, `phpwfs_bookmarks_v1`,
  `awd_bookmarks`, `awd_theme`, `tybca_sem5_last_subject`,
  `tybca_sem5_theme`) — confirms the earlier namespace-collision fix holds
  up in practice.

**Unified palette (MAJOR change per §J12B — approved via direct user
confirmation after being asked to clarify scope):**
All 3 subject files theme themselves entirely through CSS custom
properties declared once (`:root{}` / `[data-theme="dark"]{}`), referenced
via `var(--x)` throughout. This made a low-risk path available: change
only the *values* of each file's own existing variables to match the
dashboard's palette, touching zero HTML/JS/layout.
- NT already used the exact dashboard token values — no changes needed.
- AWD and PHP already used a similar indigo-family palette (not
  identical) — remapped `--bg`/`--card`/`--text`/`--muted`/`--border`/
  `--accent`-family variables (light + dark blocks) to the dashboard's
  exact hex values (`#F8FAFC`/`#FFFFFF`/`#0F172A`/`#64748B`/`#E2E8F0`/
  `#4F46E5` light; `#0B1120`/`#111827`/`#F8FAFC`/`#94A3B8`/`#334155`/
  `#818CF8` dark). Also recolored each file's decorative header gradient
  (previously mixed indigo/pink/magenta tones) to use the new accent, since
  it's highly visible. Left secondary/semantic colors (amber warnings,
  highlight/tip/important backgrounds) untouched — not part of "brand
  consistency," changing them risked breaking established meaning-color
  associations for no benefit.

**Verification:** re-ran the full functional check (search, bookmarks,
theme toggle, AWD's More menu) after the palette change on all 3 files —
all still work, no console errors. Diffs against the original files

the primary verification method, with screenshots as secondary visual
confirmation once they caught up. Worth carrying into future sessions:
trust computed-style/DOM-state checks over screenshots when they disagree
in this environment.
